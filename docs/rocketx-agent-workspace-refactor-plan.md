- 适用范围：RocketX 的个人管家、执行工作台、已有 Agent 会话接续、ADO 与 RocketX 协同、成果验收和汇报。

RocketX 要让用户把工作交给长期理解自己的个人管家，同时保留直接查看和控制多个执行 Agent 的能力。用户可以从 RocketX 发起工作，也可以先在 Codex 中开始，再由 RocketX 接入、跟进、验收和汇报。

本次重构以“工作”为日常管理对象。对话、执行尝试、外部工作项和成果围绕同一件工作关联；个人管家负责持续跟进，执行 Agent 负责具体交付。ADO 状态更新、RocketX 讨论室汇报和通知是工作流程的一部分。

本方案保留既有消息、日历、个人待办和 ADO 确定性界面。AI 协作区采用“管家 + 工作台”两个主要工作面；全局导航是否进一步调整，需要用真实使用路径单独验证。语音对话为可选增强能力，默认关闭，本轮核心交付不依赖语音、独立显卡或云端语音服务。

## 0 2026-11-17 目标校正：少量人类注意力支撑持续、可验证的交付

用户明确以 Lauren Tan（@poteto）所展示的高吞吐 Agent 工程实践为目标。本节是设计要求，不是现有能力声明。月度 PR 数量受任务规模、拆分方式、团队和基础设施影响，不承诺复现特定数字，不把拆出更多 PR 当作成功。

产品目标：用户给出目标、约束和业务取舍，管家负责拆分、委派、跟进、组织验证、返工和交付；人类无需逐个驱动执行 Agent 或替它们传递上下文。保留直接操作单项工作的入口。发布和外部写入继续遵循既有授权范围，不因自主程度提高而扩大权限。

### 0.1 三个需要共同成立的部分

- **面向用户的管家与工作界面**：提出目标、看有意义的变化、回答必要问题、查看成果和提出修改。同一项工作的对话、当前执行和成果留在一个工作现场；默认不跳转执行器管理。
- **持续运行与编排**：工作拥有持久目标、完成条件、依赖、执行归属、预算和检查点；会话是执行通道之一。UI 断开不抹掉工作状态。根据事件跟进失败、CI、评审和外部状态，避免依赖用户反复输入“继续”。
- **工程验证与交付**：独立验证者检查实际成果，问题回到责任执行者修复；将当前版本的证据绑定当前提交。代码变更、验证、合并及发布状态分别记录，不以“已生成”代替“已交付”。

### 0.2 执行与扩展约束

1. 每个独立代码任务有明确写入负责人和隔离的分支／工作树；依赖关系显式记录，共享环境中的冲突操作受调度约束。任务粒度由可独立验收决定。
2. Codex、Claude 等通过其实际支持的持续服务／SDK／协议建立原生会话和事件连接。读取历史、恢复后续轮次、控制正在运行的会话分别核实；不能用一次性 CLI 的包装声称获得实时控制。
3. 重连和恢复核对原会话身份及最后回执；写入结果不确定时先核对，禁止自动重复执行。暂停必须说明已停止的范围，原端确认前不声称停止。
4. 实现者提交成果后由独立验证者检查。UI 变更驱动运行中的真实应用和生产入口，核对可观察副作用；模拟测试用于隔离外部系统，不能代替原生控制与完整用户旅程。
5. 建立可重复执行的验证入口及功能地图：启动、健康检查、驱动真实行为、保留证据、清理隔离环境。发现连接／能力不足时明确报告，不改测试或文案来掩盖。
6. 正常执行和可恢复故障由系统处理；只把目标歧义、权限边界、预算变化及业务取舍交给用户。并行数量受已验证能力、依赖与资源限制，而非固定追求更多 Agent。

### 0.3 验收顺序与指标

先完整走通一项已有 Codex 工作：读取上下文 → 在原会话发送要求 → 运行中补充 → 查看真实成果 → 中断确认 → 重连 → 独立验收。验证不依赖切到管理页或用户重述背景。随后验证三项有隔离、有依赖的并行工作，最后验证长时间离开后的继续与汇总；前一步不成立，不扩大执行规模。

指标必须从真实运行中建立基线：每项工作的人类介入次数及耗时、每小时实际验收的工作量、从委派到交付的时间、失败恢复比例、返工和逃逸缺陷、每项验收成果的模型与计算成本。PR 数量为辅助量，不能替代这些指标；“不串会话、不重复发送、不虚报停止或完成”作为正确性不变量单独验证。

调研依据为公开工程方法，不宣称等同 Grok Bot 内部实现：

- [pstack 作者说明](https://github.com/cursor/plugins/blob/main/pstack/README.md)：质量与可验证性是扩大并行的前提。
- [Orchestrate](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)：明确写入负责人、独立验证、先跑通一个单元、按提交版本验收。
- [Verify and ship](https://github.com/cursor/plugins/blob/main/pstack/docs/guide/06-verify-and-ship.md)：验证真实产物和用户行为，建立可复用验证基础设施。

## 3 偏差处理与实施纪律

遇到未覆盖细节时，默认采用可逆、最小影响、保留原生身份与已有数据的方案，记录到实施笔记后继续。

可以直接处理：补充状态文案、修复输入与草稿行为、对不支持的能力显示明确降级、保留旧深链重定向、复用已有存储增加必要字段、为真实失败路径补测试。

以下变化需要重新讨论相应范围：不可逆数据迁移或删除、扩大账号与网络权限、改变工作业务真源、从单机转为团队共享执行、以新会话替代原会话接续、移除已承诺的核心能力。用户在后续讨论中已经明确授权的选择无需重复确认。

一个切片发生第三项实质偏差，或出现推翻方案前提的发现时，先修订该切片的计划，再继续实施。不得用不断增加兼容层掩盖边界不清。

不新增依赖作为默认解决办法。确需新增依赖时，说明现有能力为何不足、部署成本、许可证和退出方式，遵守仓库依赖约束。

## 4 用户工作流程与信息架构

### 4.1 日常对象

用户主要接触“管家、工作、项目、成果”四个概念。执行记录、事件、同步动作和审批是工作内部的过程，不要求用户分别维护。

- 管家对话允许临时问答、资料查询、起草、明确委派和后续修改。
- 工作保存一个需要持续推进的结果；创建后不因执行器更换而改变身份。
- 项目先用于收拢工作、资料和默认规则，不要求建立复杂目标层级。
- 成果可以是代码变更、文件、文档、分析结论或已完成的外部动作。
- 个人待办仍可独立存在；勾选个人待办不自动等价于 Agent 工作通过验收。

### 4.2 两个主要工作面

| 工作面 | 默认回答的问题 | 主要内容与动作 |
| --- | --- | --- |
| 管家 | 我可以交代什么，之前的事怎么样了 | 连续对话、工作引用、简短回执、需要决定的问题、近期变化 |
| 工作台 | 哪些工作正在推进，我要接管哪一个 | 稳定工作列表、项目过滤、需要你／进行中／等待／已交付视图、工作详情 |

工作详情沿用同一上下文呈现当前要求、执行过程、成果、验证和外部同步。用户可以展开多个工作进行比较；默认不强制所有面板同时常驻。

“需要你”从持久化的澄清、审阅、审批与阻塞事项派生，不另建第二套任务。项目过滤和任务详情应保留返回位置。成果首先在所属工作与项目内检索，暂不增加必须维护的独立成果库入口。

连接、运行时、模型、权限、记忆和技能配置归入设置或项目设置。高频的执行器切换可在工作上下文中提供，但不是每次发消息的前置步骤。ACP、Runtime、Lease 等实现术语不作为日常操作名称。

既有消息、日历、联系人、个人待办和 ADO 列表继续可达。它们通过来源链接与工作关联，不复制一套影子业务数据。

### 4.3 五条主要用户旅程

| 场景 | 期望流程 | 可见结果 |
| --- | --- | --- |
| 从自然语言开始 | 交代目标 → 系统识别必要上下文 → 建立工作 → 委派 | 一条简短回执和同一工作的进展入口，无需手动绑定会话 |
| 从 ADO 或消息开始 | 对来源执行“交给管家” → 带入原文与链接 → 确认必要歧义 | 任务关联正确来源，后续回报可返回原位置 |
| 接入已有 Codex 工作 | 发现原会话 → 查看 → 识别控制能力 → 顺序接续或连接原服务 | 原生会话 ID、工作目录和历史不被悄悄替换 |
| 中途修改与接管 | 在工作详情补充要求 → 更新要求版本 → 交接控制 → 反馈生效范围 | 用户知道旧执行是否已停止、新要求何时被接受 |
| 离开后回来 | 查看新增结果、待决定与阻塞 → 定位成果 → 继续 | 不需要重读完整聊天或重新交代背景 |

### 4.4 必须验收的体验细节

| ID | 用户情境 | 行为要求 |
| --- | --- | --- |
| UX01 | 第一次打开已有开发环境 | 先发现已有执行器、账号状态、项目和近期工作；缺什么补什么，不要求重新配置全部能力 |
| UX02 | 发现大量历史会话 | 默认显示近期与相关工作；不把全部历史自动转成工作卡；来源和时间清楚 |

| UX14 | 处理审批或问题 | 请求属于明确工作，内容、目标、有效性和影响范围可见；失效请求不能继续操作 |

| UX18 | 工作数量增长 | 用项目、标题、ADO 编号、文件名检索；列表更新不让点击目标突然移动 |

草稿的建议身份为“账号作用域 + 工作或原生会话身份 + 接收对象”。发送时冻结该目标，异步结果返回时不得按当前页面焦点重新路由。

附件先进入受管本地存储，再形成可恢复引用；不能依赖页面卸载后失效的临时 URL。上传或准备失败的附件保留在原草稿，并可单独处理。

## 5 工作记录与状态合同

### 5.1 最小领域关系

以下是逻辑边界，不要求立即新建同名数据库表。当前工作卡由 todos 与 work_card_states 组合，另有 work_sessions、work_links、work_evidences、external_events 和 dispatch_actions，应优先复用这些基础。

~~~text
项目
  └─ 工作
      ├─ 当前要求与验收条件
      ├─ 执行记录 A → 原生 Codex 会话
      ├─ 执行记录 B → 另一执行器或重试
      ├─ 成果与验证证据
      ├─ 待决定事项
      └─ ADO、消息、PR、构建等外部联系与操作回执
~~~

工作状态由协调服务维护，原生会话历史仍由执行器负责，ADO 业务状态仍由 ADO 负责。RocketX 可缓存有来源和时间的投影，但不能把缓存视作永不过期的真源。

### 5.2 建议的最小合同

~~~ts
type WorkIdentity = {
  workId: string;
  accountScope: string;
  projectRef?: string;
  legacyTodoId?: string;
};

type WorkInstruction = {
  workId: string;
  revision: number;
  objective: string;
  acceptance: AcceptanceCriterion[];
  contextRefs: string[];
  executionPolicyRef: string;
};

type NativeSessionRef = {
  hostId: string;
  providerProfileId: string;
  nativeSessionId: string;
  workspaceRoot: string;
  source: 'rocketx' | 'native-cli' | 'native-desktop';
};

type ExecutionRecord = {
  runId: string;
  workId: string;
  instructionRevision: number;
  nativeSession: NativeSessionRef;
  status: 'queued' | 'starting' | 'running' | 'waiting'
    | 'finished' | 'failed' | 'interrupted' | 'unknown';
  controllerOwner?: string;
  lastObservedAt: number;
};

type AcceptanceCriterion = {
  id: string;
  description: string;
  verification: 'mechanical' | 'human' | 'external';
  required: boolean;
};
~~~

具体字段名称可沿用现有实现。第一阶段已纳入跟进的工作可沿用 todo.id 作为 workId，避免无必要地重建身份；普通个人待办不因此进入执行流程。work_sessions 表示原生会话关联，不等同于一次执行尝试；执行尝试应结合现有派发动作、原生 turn 引用和要求版本记录。新增字段前核对当前结构，不为匹配示例而整体迁移。

原生会话去重不能只用 sessionId；至少包括宿主、提供方配置和原生会话 ID，并纳入账号作用域。一个原生会话在首版至多绑定一个当前工作；迁移绑定需保留记录，避免同一输出被多个工作分别认领。

配置别名若指向同一个原生数据源，应先归一化为稳定来源身份，不能因重命名或新增配置别名复制会话。当前 SQL 唯一键及 upsert 查找仍使用 runtime 与 native_session_id；接入多个来源作用域前，必须同步调整持久层唯一键、查找方式和旧关联迁移。暂不迁移的切片只能明确支持单一来源作用域，不能只修改前端键。

### 5.3 四类状态分别判断

| 维度 | 示例 | 决定依据 |
| --- | --- | --- |
| 工作阶段 | 待明确、就绪、执行中、核验中、完成 | 当前要求、验收条件和验证结果 |
| 等待或控制状态 | 等待输入、等待审批、等待外部、阻塞、暂停、取消 | 对应请求、控制回执和恢复条件 |
| 执行状态 | 排队、运行、等待、结束、失败、中断、未知 | 原生运行服务的事件或经核实的观察 |
| 外部动作状态 | 未请求、待执行、发送中、已确认、冲突、失败、结果未知 | 来源版本、发送记录与回读结果 |

已有 stage 与 waitState 的正交设计可以继续使用，不必先新增大枚举。界面从这些事实派生“进行中”“需要你”“等待”“已交付”等用户视图。

- 执行结束只表示本次运行结束，不能直接完成工作。
- 工作通过验收不表示 ADO 已更新，也不表示汇报已送达。
- 无有效观察时标记未知或失联，不能根据日志不增长推断空闲。
- 暂停跟进不自动停止所有原生进程；取消执行需要原生回执。
- 取消工作阻止后续自动派发，已完成的外部动作仍保留其真实状态。

已纳入跟进的工作，其完成状态由工作验收合同决定。旧待办勾选、ADO 快照刷新和兼容投影不得直接覆盖工作阶段或清除等待状态；普通个人待办仍保留原有完成行为。若项目允许人工验收，完成操作应记录用户明确接受的条件与身份，不能仅把 todo.done 改为 true 后触发完成汇报。

### 5.4 要求版本与控制权

用户实质修改目标、边界或验收条件时，增加 instructionRevision。旧执行结果可以保留为历史，但不能直接冒充当前版本的完成依据。

同一可写工作区在同一时间需要明确控制方。编码并行优先使用已有 worktree 隔离；无法隔离的共享目录先排队。首版不设计自动合并任意 Agent 修改的通用机制。

宿主控制的写操作在执行前核对要求版本与授权范围。执行器内部已经开始的动作无法仅靠本地字段保证立即撤销，因此取消未确认时应展示“停止请求处理中”或“状态未知”，并在后续读取实际结果。

## 6 架构与运行边界

### 6.1 两类 Agent 和共同工作服务

~~~mermaid
flowchart TD
    U[用户] --> C[管家对话]
    U --> W[多 Agent 工作台]
    C --> P[长期个人管家]
    P --> S[工作协调服务]
    W --> S
    S --> L[工作账本与事件回执]
    S --> A[执行器适配]
    A --> X[Codex Pi 及其他已验证执行器]
    S --> B[ADO 与 RocketX 业务适配]
    L --> R[成果 验证 汇报与通知]
    R --> C
    R --> W
~~~

工作协调服务提供确定性的记录、控制、事件与投递能力，不是第三个“大脑”。用户和管家使用同一组工作命令；工作台不是运行服务本身。

个人管家负责理解、拆分、选择下一步、总结和在边界内跟进。执行器负责原生模型调用、工具与会话。宿主负责工作身份、操作去重、来源权限、控制归属和持久化。

当前 Pi 默认运行时与 Codex 命名的兼容接口需要明确区分。发现外部 Codex 会话后，必须进入真正的 Codex 适配，不能把外部 ID 送入 Pi 运行时并显示为“已恢复”。

### 6.2 后台服务的最小范围

把持久事件处理、待决定事项、定时触发与投递恢复放到不依赖 React 页面挂载的宿主路径。可以使用现有 Tauri／Rust 模块和已有 sidecar 进程；不预设新消息中间件或工作流引擎。

前端订阅投影、提交命令并呈现反馈。路由切换、当前 activeThreadId 和 workspaceRoot 不应成为后台派发的定位依据。每个命令显式携带 workId、目标会话与环境。

### 6.3 本地运行承诺

| 用户动作或环境变化 | 首版承诺 |
| --- | --- |
| 切换页面、最小化或关闭到托盘 | 宿主仍运行时，工作与事件处理继续 |
| 前端重载 | 重建订阅并恢复投影，不重新发起同一业务动作 |
| 主动退出 RocketX | 明确受影响的受管执行；记录检查点和未决操作；不承诺进程退出后仍持续执行 |
| 原生 Codex 由外部独立启动 | 不因关闭 RocketX 就默认终止外部工作 |
| 电脑休眠或关机 | 不承诺期间推进；恢复后补读状态、核对回执和计划 |
| 网络中断 | 保存命令意图与已有结果；只对已确认可重试的步骤恢复执行 |
| 宿主异常退出 | 重启先对账已提交动作，区分继续、重试、冲突和需要人工处理 |

是否提供独立常在线内网宿主属于 D08 的后续决策。界面需要始终能解释“这项工作在哪里运行、当前是否在线”。

## 7 接入已有 Codex 工作

### 7.1 观察与控制分开

| 能力等级 | 条件 | 可执行操作 |
| --- | --- | --- |
| 只读可见 | 可以读取会话记录，但没有经确认的控制通道 | 查看标题、工作目录、已保存历史和观察时间 |
| 可恢复 | 原会话可被当前版本恢复，且通过受支持的状态核验或明确交接确认可以独占顺序接续 | 沿原 ID 顺序继续，接收新执行事件 |
| 可实时控制 | 已连接持有该会话的运行服务，且具备相应控制权限 | 追加要求、中断、处理对应请求 |
| 不可访问 | 账号、宿主、工作目录或记录不可访问 | 说明原因；不展示必然失败的恢复按钮 |

未知控制状态默认只读。读取 SQLite 或 JSONL 不等于连接原来的执行进程，不能据此开放实时控制。

### 7.2 原生接续流程

1. 发现已配置或可访问的 Codex 数据目录，包括明确配置的 CODEX_HOME；不只假定默认目录。
2. 展示来源、宿主、工作目录、更新时间及历史覆盖范围。
3. 使用完整原生身份去重。用户选择“纳入跟进”时建立工作关联，重复选择返回同一工作。
4. 探测原生运行状态、适配器能力和控制归属。不能确认时保留只读。
5. 空闲会话通过经过版本验证的原生恢复机制继续；当前 CLI resume 路径可作为待验证实现。
6. 运行中的会话优先连接原运行服务；无法连接时，提示在原端完成或停止后顺序接续。
7. 继续执行时保留原 ID、工作目录及必要配置，记录后续指令与 RocketX 工作的关联。
8. 从 Codex 回到 RocketX 后重新读取原生新增内容，更新同一工作，不生成第二套历史真源。

若目标无法恢复，应明确失败原因。不得静默创建新会话并称为“继续原会话”。用户选择复制上下文到新会话时，必须显示新身份与来源，保留原记录。

### 7.3 接口与兼容性

官方 app-server 提供 thread/read、thread/resume、turn/start、turn/steer、turn/interrupt 等能力 [R08]。这些操作只适用于实际连接、支持该接口的运行服务，不能推导为任意外部桌面进程都可直接控制。

适配器应按实际探测返回“读取、恢复、实时订阅、运行中追加、中断、审批、附件、工作区隔离”的能力。缺少原生 steer 的执行器可以明确提供“停止后发送”或“排队”，不得以相同按钮伪装成实时追加。

首版对当前实际安装的 Codex 和项目支持版本建立验证矩阵。只读发现、原 ID 恢复和活动会话控制分别记录验证结果；不以协议生成类型或硬编码 true 代替证据。

## 8 调度 跟进与人工介入

### 8.1 事件进入工作

事件处理顺序为“保存原始来源与去重键 → 关联工作 → 核对来源当前状态 → 判断需要采取的动作 → 持久化动作意图 → 执行并记录回执”。

外部消息和 ADO 评论属于上下文，不能自动成为扩大权限的指令。弱关联事件先进入待明确状态；不能仅凭相似标题写入另一个工作项。

实时消息、重新联网后的补偿读取和定时检查应走相同的关联与去重规则。恢复时的历史补读不等于重放所有历史副作用，应使用检查点、来源版本和当前状态判断是否仍有未完成责任。

### 8.2 持久等待与审批

待决定事项至少保存所属工作、要求版本、动作类型、内容摘要、来源、创建时间、状态和恢复引用。原生内存 Promise 可以服务一次连接，但不能是唯一恢复依据。

重启后先检查请求是否仍有效。原生请求已消失、目标内容变化或执行状态改变时，标记失效并重新建立正确的继续路径。点击旧审批卡不能向另一个会话发送结果。

预先授权范围内的常规步骤自动继续。只在缺少必要信息、需要业务判断或超出既定范围时找用户，避免把每个写操作都变成重复确认。

### 8.3 并发 预算与重试

- 按实际执行宿主限制并发；同一未隔离可写目录先串行。
- 保留已有自动轮次预算，补充任务时长与未达标尝试次数；有可靠用量信息时再增加金额或 token 上限。
- 区分派发失败、工具失败、验证失败和业务条件未满足；“指令送达”不能清零所有工作失败记录。
- 瞬态只读失败可以有界退避；外部写入结果未知时先回读或对账。
- 预算耗尽、持续无进展、执行器不可用时明确转为等待或阻塞，保留已经取得的成果。

### 8.4 停止语义

| 操作 | 行为 |
| --- | --- |
| 停止本轮执行 | 向对应执行器请求中断，记录是否得到确认 |
| 暂停自动跟进 | 不再自动启动后续轮次，当前运行是否停止由明确选项决定 |
| 暂停整件工作 | 停止新派发，并处理当前执行和待投递动作的状态 |
| 取消工作 | 终止未来推进责任，保留历史、已完成动作与尚需核对的结果 |
| 取消周期计划 | 停止未来触发，不伪装成撤销既有运行 |

## 9 业务同步 成果与上下文

### 9.1 ADO 与 RocketX 的数据归属

| 数据 | 权威来源 | RocketX 保存什么 |
| --- | --- | --- |
| ADO 标题、负责人、业务状态、项目流程 | ADO | 外部 ID、版本、读取时间与必要快照 |
| 原生 Agent 会话与执行事件 | 对应执行器或运行服务 | 引用、受管执行记录及可恢复投影 |
| RocketX 消息与讨论室 | Rocket.Chat 服务端及现有客户端存储 | 消息身份、所属工作与投递回执 |
| 工作目标、当前要求、验收与跟进责任 | RocketX 工作账本 | 持久协调状态 |
| 用户偏好、项目约定和长期背景 | 明确作用域的记忆或版本化项目资料 | 来源、纠正记录和有效性 |

首版每个项目需要一份可查看的同步规则：哪些字段只读，哪些状态可自动更新，什么条件触发汇报，哪个账号和讨论室接收结果。规则应有版本，任务开始时保留所采用的版本引用。

### 9.2 外部动作合同

外部动作意图包含 workId、要求版本、目标资源、预期来源版本、动作摘要与稳定操作 ID。发送前记录意图，完成后记录服务端回执或读取验证结果。

建议状态沿用或适配现有 dispatch_actions：

~~~text
prepared → sending → acknowledged
                 ├→ conflict
                 ├→ failed
                 └→ unknown → reconcile → acknowledged / failed / needs_input
~~~

同一来源事件或同一操作重试不应生成新的业务身份。网络无法确认写入结果时保留 unknown；只有确认未发生或具备端到端幂等保证后才重试。

对于聊天汇报，先核对目标服务是否支持客户端消息 ID 或等价幂等机制。若无法可靠查明是否送达，显示“送达待确认”，不能承诺严格一次投递，也不能盲目重复发送。

ADO 被他人修改时展示最新状态与冲突，不用旧快照覆盖。需要重新判断的状态转换回到原工作；已通过的代码验证无需因此重复执行。

### 9.3 汇报合同

每次汇报面向明确对象，默认内容为：已完成什么、依据和成果、未完成或受阻部分、下一步及需要谁决定。报告应包含来源链接和必要的观察时间。

报告引用冻结的事实快照及版本。报告发布后发生新变化，可以生成明确的新版本或更正；不能悄悄改写原始完成事实。

报告草稿、用户审阅、已发送和送达未知分开显示。发送到讨论室之前校验目标与内容的可见性，不把个人背景、私有附件或其他项目的内容混入共享汇报。

### 9.4 验收与成果

成果至少有稳定引用、所属工作、版本或内容标识、生成来源、位置和适用要求版本。代码证据关联相应 commit／worktree 状态，文档和分析证据关联相应内容版本。

每条必要验收条件映射到具体证据。测试通过、外部状态确认、用户验收与 Agent 自述使用不同证据类型。Agent 汇报可以解释结果，但不能单独把未通过验收的工作变为完成。

修改成果后，受影响的旧证据失效或需要重新核验。仅有一条不相关通过证据不足以完成整件工作。用户明确接受例外时记录接受了什么，不能伪造成机械验证通过。

失败后的返工沿用同一工作，创建新的执行尝试；保留前一次成果、失败依据和当前有效版本。

### 9.5 记忆 项目资料与权限

优先复用现有账号／工作区作用域、来源和启停删除能力。将个人偏好、项目约定、历史决定和临时执行事实分别处理。

- 长期记忆可查看来源、纠正、删除或停用。纠正后，旧版本不能继续被默认召回。
- ADO 当前状态等易变事实保留来源引用，使用前按需重新读取。
- 强制项目规则进入版本化项目资料或技能，不依赖模糊记忆维持授权。
- 委派只附带当前工作需要的上下文；团队共享不自动公开私人管家历史。
- 检索结果说明来源、覆盖范围和更新时间；没有搜索到不等于来源中不存在。
- 暂不要求引入向量数据库。先验证关键词检索、引用资料与现有历史查询能否解决首批问题。

### 9.6 技能 连接与就绪状态

将已验证的一次性流程保存为技能，明确输入、输出、验证和失败处理，再按需要连接定时或事件触发。优先利用现有周报、消息汇总、承诺提取和评审相关技能。

执行器已安装、账号已登录、服务可达、某项工具已授权和某项能力可用是不同状态。只显示当前已验证的可操作入口，失败原因要能引导到重新登录、重连、选择环境或查看诊断。

### 10.1 已观察到的优先风险

1. workflowReport 的 recordReportAsWorkEvidence 会把 verifying 报告记为 passed；原生 normalize_work_evidence_kind 又将 agent_report 映射成 manual_ack，完成门禁接受任意有效通过证据。存在报告自证完成及证据来源退化的静态代码路径，尚未实机复现；需先写行为测试再修复。
2. Codex 本机扫描记录的 runtime_status 当前固定为 idle。活动会话保护不能依赖该值，应先阻止未经确认的并发接续。
3. ACP 输入回车处理缺少与管家输入一致的组合输入保护；单一输入状态与失败后写回旧文本需要验证跨会话草稿和覆盖问题。
4. 右侧面板分别回退选择工作卡和 ACP 会话，随后合成报告；应保证三者同属明确工作。
5. SuperAgent 跟进依赖前端聊天订阅，并跳过历史首屏；现有例行任务和托盘能力不等于全部恢复链路已贯通。
6. ADO 受控写函数在本次 apps/web/src 调用扫描中未发现生产调用；汇报发送路径尚未证明具备持久去重和不确定结果恢复。
7. 原生 sync_card_state_on_todo_write 与前端 todoToNativeCard 会根据 todo.done 把工作阶段投影为 done。只修改完成门禁不能覆盖这条兼容入口，需同步约束已纳入跟进工作的完成权。

### 10.2 必须提前验证的失败场景

| 场景 | 可能后果 | 验证与约束 |
| --- | --- | --- |

### 11.2 数据与入口迁移

1. 保留本机原生 Agent 会话及其 ID，不批量重写原生日志。
2. 保留现有 todos 和工作账本关系；先增加最小必要字段与投影，不立即重建整个任务领域。
3. 区分个人待办与已纳入跟进的工作；没有显式委派的历史待办不自动执行。
4. 旧工作、会话和外部资源使用确定性映射；重复迁移不重复建卡或发起执行。
5. 迁移前记录版本和可恢复快照；数据库变更采用事务或可恢复步骤，并验证中途中断。
6. 原生运行中会话、待审批事项和结果未知的外部写入需要单独对账，不按普通静态记录迁移。
7. 旧深链、收藏和历史入口先重定向到同一对象；确认可达后再移除重复可见入口。
8. 只删除本轮变更产生的孤儿代码；无关遗留问题单独记录。
9. 每个切片保留切回旧入口的方式。若旧版本不能读取新字段，应先限定试用范围，不伪称可无损回退。
10. 实施完成后同步功能规格、能力矩阵和测试追踪；本计划转为历史记录，不能长期代替现状文档。

原生会话身份迁移必须覆盖 SQL 唯一键、记录查找、upsert 和外键关联。用两个不同来源中相同 nativeSessionId 的样本验证不会合并；若首个切片仅支持单一作用域，第二来源必须被明确拒绝或保持只读，不能覆盖原记录。

历史 manual_ack 若不能证明来自真实人工验收，不得直接作为新要求版本的完成依据；保留原记录及来源不确定标记，不自动回退已经完成的外部业务状态。普通个人待办迁移后仍可勾选完成；关联工作的完成操作必须经过同一验收路径。

### 11.3 可选语音

语音是同一个个人管家的输入与输出方式，复用文字工作状态，不创建独立语音任务系统。

采用本地 CPU 语音识别与语音合成的候选方案，例如 sherpa-onnx [R09]；文字理解和执行沿用现有可用 Agent 接入。模型按需取得并核对许可证，语音关闭时不加载模型、不持续监听麦克风。

先验证按住说话、可见转写、短答播报，再评估自动断句、打断播报和回声处理。打断播报与取消后台工作是不同动作，关闭语音不终止已经委派的工作。

中文夹杂项目名、ADO 编号和技术词的准确率，以及端到端延迟，必须在目标机器实测。没有测量结果前，不承诺达到 GPT Live 的自然度或延迟。独立显卡不是核心重构前置条件。

## 12 验证与交付标准

### 12.1 主业务场景

在已配置仓库、执行器、ADO 项目与汇报讨论室的环境中，用户交代：

> 处理这个 ADO 缺陷，验证后按项目规则更新状态，并在对应 RocketX 讨论室汇报。

系统建立一件工作，关联来源并启动执行。用户从工作台进入补充要求；管家仍可回应其他问题。完成后展示成果和独立验证证据，再进行授权范围内的状态更新与汇报。重开界面后仍是同一件工作。

### 12.3 必须走过的用户操作

1. 输入中文长要求并附图，切换三个工作后返回，检查草稿、附件和发送目标。
2. 两个执行器运行时阅读旧结果，观察新事件是否抢焦点、移动列表或强制滚动。
3. 发送失败后继续输入新内容，再恢复连接，检查旧请求重试与新草稿分别保留。
4. 在 Codex 开始工作，由 RocketX 顺序接续，再回到原生记录查看新增结果。
5. ADO 更新成功、汇报失败，只恢复汇报，并清楚展示两部分状态。
6. 在审批等待、网络中断和程序重启后，继续同一工作并核对外部动作没有重复。
7. 使用真实规模数据测试：至少 100 项工作、长标题、相似项目名和跨工作搜索；不只用几张示例卡验收。

### 12.4 性能与体验观察

以下数值是建议的初始目标，不是已测性能；S0 记录目标机器与数据规模，S1 根据基线确认。

| 指标 | 初始目标或记录方式 |
| --- | --- |
| 本地发送操作的可见反馈 | P95 不超过 200 ms，不等待模型响应 |
| 已缓存工作之间切换 | P95 不超过 500 ms，草稿和滚动位置保持 |
| 本地收到执行事件至界面更新 | P95 不超过 1 s；外部网络耗时单独记录 |
| 长时间后台使用 | 检查持续运行后的内存、CPU、事件积压和界面响应，无无限增长趋势 |
| 模型首字与业务完成时间 | 分段记录排队、接入、模型、工具、验证和投递，不给无法兑现的统一时限 |
| 日常委派成本 | 统计首次接入到第一次成功、每件工作重复交代与手动绑定次数 |
| 通知质量 | 记录用户忽略、暂缓、明确反馈和需要决策的比例；不只统计发送数量 |

普通进度用真实步骤和最近活动表达。只有存在明确可计量的分母时才显示比例，并说明它衡量的是步骤、文件还是验证项。

### 12.5 测试与证据规则

源码字符串断言只能证明结构存在，不能代替用户行为、原生执行和外部写入验证。对关键路径使用领域测试、持久化／故障注入、UI 操作和受控真实服务验证。

实现切片应按受影响范围运行检查；命令存在不代表当前基线已通过：

~~~powershell
pnpm typecheck
pnpm check:architecture
pnpm test:pure
pnpm test:regression
pnpm test:ui -- tests/ui/butler-workspace.spec.ts tests/ui/butler-host-input.regression-1.spec.ts
pnpm build
cargo fmt --check --manifest-path apps/desktop/src-tauri/Cargo.toml
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml
~~~

变更原生协议时补相应协议和真实生命周期检查，先核对仓库脚本是否仍适用于所选运行时。真实 ADO 与 RocketX 写入在明确的测试项目和讨论室验证，不能用生产数据试错。

每条验收记录环境、运行时版本、输入、可观察结果、关键回执或日志及未覆盖范围。与本切片无关的既有失败单独记录，不通过弱化断言或改变无关代码掩盖。
