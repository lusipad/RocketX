## 规格 A：终结版本面漂移（阻断发版的机制性根因）

### 根因

版本号有 **13 个受控落点**，权威清单是 `scripts/verify-release.mjs` 的 `verifyVersions()`：
8 个 `package.json` + `apps/desktop/src-tauri/Cargo.toml` + `Cargo.lock`（`[[package]] name = "rocketx"` 那节）
+ `tauri.conf.json`，外加三处文档断言（`CHANGELOG.md`、`docs/release/README.md`、`docs/compatibility.md`）。

仓库里**只有验证端，没有写入端**（`scripts/` 下仅 `verify-release.mjs` / `verify-release-assets.mjs` / `release-notes.mjs`）。
后果：v0.44.1～v0.44.11 的 7 个候选里 5 个在发布最后一刻被 gate 拦下。

### 交付物

1. `scripts/sync-version.mjs`，用法 `pnpm sync-version <x.y.z>`
   - **必须复用 `verify-release.mjs` 导出的 `packageFiles` 清单**，绝不另抄一份。
     两份清单各自漂移 = 把今天的 bug 复制一遍。
   - 文档三处按现有措辞改写：
     `CHANGELOG.md` 的 `## vX.Y.Z - <date>`、
     `docs/release/README.md` 的 ``current release target is `vX.Y.Z` ``、
     `docs/compatibility.md` 的 ``RocketX `vX.Y.Z` desktop line is split.``
   - CHANGELOG 若无该版本条目 → **报错退出**，不自动编造（发版说明必须人写）。
2. `pnpm precheck:release` —— 本地跑完 gate 的全部断言（含 `release-contract.test.ts`），
   红了当场知道，不必等 CI 的 75 秒。

### 验收

- 故意把 `docs/compatibility.md` 改回旧版本 → `precheck:release` 必须红，且**指名报出是哪个文件**。
- `pnpm sync-version <下一个版本>` 后 `release-contract.test.ts` 6/6 绿。
- **新增回归：断言 `sync-version` 覆盖的文件集合 == `verifyVersions` 检查的集合**（集合不等就红）。
  这条是防漂移的核心，不要省。
- `pnpm test:regression` 保持全绿。

## 规格 B：#388 灯箱点空白关闭

### 根因（已定位，勿重查）

`apps/web/src/components/ImageLightbox.tsx`
- `:146` backdrop 已有 `onClick={onClose}`，功能本来就在。
- `:232` stage 是 `h-[86vh] w-[92vw]` 的巨型透明画布，`:226` 挂了 `onClick={(e) => e.stopPropagation()}`。
- → 用户点的「空白」绝大部分落在 stage 内被吞掉，只有最外圈窄边能关闭。
- 该 stage 是 v0.44.5 为修「小图放大后看不见」引入的（固定视口画布），修 A 引入了 B。

### 两个必须避开的陷阱

1. **不能直接删 stage 的 `stopPropagation`** —— `:227` 拖拽与 `:252` OCR 文字层依赖它。
   正确做法：把 `stopPropagation` 下沉到内层图片承载 div（`:235`）和 OCR 层，
   或在 stage 的 `onClick` 里判定 `e.target === e.currentTarget`。
2. **拖拽结束会触发 click** —— `zoom !== null` 时可拖拽，拖完松手若被判为「点空白」就会误关。
   必须区分点击与拖拽（如 mousedown→mouseup 位移阈值）。

### 验收

`tests/ui/core-flows.spec.ts` 新增用例：
点 stage 空白关闭 ✓ / 点图片本身不关 ✓ / 点工具栏不关 ✓ / **拖拽平移后松手不关** ✓。
`pnpm test:ui` 与 `pnpm test:regression` 双绿。

## 规格 C：LAN 服务器身份 + 过滤层诊断（#369）

### 根因（正向代码分析，非日志推断）

前 6 轮修复全在「怎么把包发出去」。但公告收到后还有一道闸：

`apps/desktop/src-tauri/src/lan.rs:246-268` `record_peer()` —— 8 个条件任一不满足直接 `return`，**零日志**：

```rust
if announcement.version != PROTOCOL_VERSION
    || announcement.server_fingerprint != local.server_fingerprint   // ← 嫌疑
    || announcement.device_id == local.peer.device_id
    ... { return; }   // 静默丢弃
```

过不了闸 → `peers` 空 → `peer_candidates()` 空（`:1251`）→ `"no LAN peer is online for this user"`（`:1253`）。

指纹为何不等，见 `apps/desktop/src-tauri/src/native/lan_identity.rs`：
- `:13-14` 注释：不做 DNS 解析，**主机名与 IP 视为不同服务器**（localhost 除外）。
- `:74-87` `server_url_aliases()` 别名表**只有** `localhost` ↔ `127.0.0.1`。
- `:162-172` 测试自身断言 `host-a` ≠ `host-b`、`http://…` ≠ `https://…`。

因此下列组合**永远发现不了对方**：
`http://192.168.1.10:3000` vs `http://myserver:3000`（IP vs 主机名）；
`http://chat.corp:3000` vs `https://chat.corp`（HTTP vs HTTPS 入口）。

**诊断盲区**：v0.44.0 的 `lan_diagnostics` 只记「发包数 / 候选发现 / 连接结果」，
而候选日志（`:309`）**只在通过全部过滤之后才打**。
被指纹过滤掉的公告，在日志里与「根本没收到包」**无法区分**——盲区恰好盖住最可能的根因。

### 交付物

**C1. 过滤层诊断（先做，独立可发布）**

`record_peer` 每个拒绝分支打 `LAN_LOG_TARGET` 日志，写明**拒绝原因分类**
（`version` / `server_fingerprint` / `self` / `malformed`），
并单独统计「收到但因指纹不匹配而丢弃的公告数」。

安全约束不变：**不得记录 IP、端口、user_id、device_id、公钥、指纹原文**，只记原因枚举与计数。
沿用现有 `lan_diagnostics` 白名单测试的写法。

**C2. 指纹改用服务器自报身份（已获批准放宽 IP↔主机名）**

方向：**指纹不再由「客户端怎么连」决定，改由「服务器是谁」决定。**
这样 IP / 主机名 / HTTP / HTTPS 接入同一台 RC 都得到相同指纹，
且不同服务器天然不同 —— 既满足放宽，又不牺牲跨服务器隔离，也不需要 DNS 解析。

实施顺序（**第 1 步是验证，不要跳过**）：
1. 先确认 Rocket.Chat 8.6.1 的 `/api/v1/settings.public?_id=uniqueID` 是否可读。
   **本轮未能验证**（本机 3300 实例未运行），结论以实测为准。
2. 指纹输入优先级：`uniqueID` → `Site_Url` → 当前接入 URL 归一化（现行为兜底）。
   `apps/web/src/lib/client.ts:100-124` 已有 `settings.public` 读取与 `Site_Url` 缓存，复用它，不新建链路。
3. **兜底必须保留**：`Site_Url` 未配置或仍是默认 `http://localhost:3000` 时不可作为指纹
   （多台服务器会撞车），此时回退到现行的接入 URL 归一化。
4. 版本兼容：新旧指纹算法不同，混合版本组网会互相发现不了。
   在 announcement 里带上指纹算法版本，或同时广播新旧两种指纹，二选一并说明理由。

### 验收

- C1：新增 Rust 测试断言**每个**拒绝分支都产生对应分类日志，且日志不含敏感字段。
- C2：新增测试覆盖 IP / 主机名 / HTTP / HTTPS 四种接入方式指纹一致；
  两台不同服务器（不同 `uniqueID`）指纹不同；`Site_Url` 为默认 localhost 时正确回退。
- `cargo fmt --check`、Rust 全量测试、`pnpm test:regression` 全绿。

## 规格 D：图片失败原因可见（#382）

### 根因

`apps/web/src/components/AuthImage.tsx:22-31`：

```js
rest.fetchFile(path)
  .then((blob) => imageBlobWithDetectedMime(blob, path))
  .then((blob) => { ... })
  .catch(() => null)      // ← 401/404/网络/Tauri 通道/嗅探异常，全部塌缩
```

所有失败原因塌缩成 `null` → `setFailed(true)` → 统一显示「图片加载失败」。
线上不产生任何可区分信号 —— 这才是 #382 八轮评论后停在「请提供失败样本」的机制性原因：
**不是缺样本，是客户端不产生证据。**

次要嫌疑（未证实，列为观察项）：`apps/web/src/lib/imageMime.ts:17` 嗅探窗口仅 512 字节，
SVG 靠文本特征识别（`:66-72`），若文件以超过 512 字节的注释头开头且无 `<?xml` 声明则嗅探失败，
通常由 `.svg` 扩展名兜底，但**缩略图 URL 未必带扩展名**。

### 交付物

1. `loadAuthedBlob` 的 `.catch` 保留错误分类（HTTP 状态 / 网络 / 解码 / 空响应），
   经 `console.warn` 或既有诊断通道输出。UI 文案可保持「图片加载失败」不变，
   但**错误对象不能被吞**。
2. 不改 `blobUrlCache` —— 已实测其 LRU 与 `protectedKey` 行为正确，无 use-after-revoke 竞态。

### 验收

新增回归覆盖 401、网络中断、空 blob 三种失败，断言各自产生**可区分**的诊断信息；
`pnpm test:regression` 与 `pnpm test:ui` 全绿。
