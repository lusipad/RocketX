# 产品原则：GTD、注意力与 AI 协作

这组原则约束所有功能规格。它们不是营销语，而是设计和验收时的判断标准。

## 1. GTD 是工作流，不是另一个信息仓库

RocketX 使用五个连续动作组织工作：

1. **捕获**：从消息、工作项、文件或自然语言中接住需要处理的事。
2. **明确**：区分信息、下一步行动、等待他人、日程和可删除内容。
3. **组织**：把确定事实放回消息、工作台、待办、日历或项目，而不是只留在 AI 对话里。
4. **回顾**：用摘要、例行检查和可追溯来源重新判断优先级。
5. **执行**：用户选择当下要推进的结果；管家协助理解、编排和执行。

因此，AI 回答不是最终数据模型。工作项状态、待办、日历、消息和配置必须落在对应的确定性界面中。

## 2. 注意力是稀缺资源

- 默认界面保持安静；低频设置和过程细节按需展开。
- 通知必须对应用户关注、明确提及、失败或需要决策的事件。
- 空状态告诉用户下一步，不堆叠概念或功能清单。
- 自动化先做本地预检，没有新信息时不启动昂贵的 AI 任务。
- 运行过程可以折叠，但审批、失败、来源和最终结果必须可找到。
- 不用“智能”掩盖不确定性；无法确认就明确说无法确认。

## 3. 确定性界面与 AI 各司其职

| 确定性界面负责 | AI 管家负责 |
| --- | --- |
| 展示权威事实与完整列表 | 理解自然语言目标 |
| 编辑结构化字段 | 选择合适 Skill 和工具 |
| 明确保存、撤销和冲突 | 汇总、解释、规划和执行多步工作 |
| 给出可复现查询和链接 | 在需要时请求审批或补充信息 |

同一能力如果已经有可靠 API、工作台或表单，AI 应调用它或引导到它，不能再造一套影子数据。

## 4. Skills 承载可重复行为

标准化、可复用且有固定输入输出的工作流应进入 Skill；临时对话只描述本次目标。Skill 可以被自然语言自动选择，也可以由用户显式指定。插件用于分发包含 Skills、连接器或 MCP 工具的可安装能力。

这与 OpenAI Docs 对 Skills 和 Plugins 的定义保持一致，但 RocketX 是否支持某个具体安装或调用流程，仍以本仓库规格为准。

## 5. Memory 是轻量召回，不是规则数据库

Memory 用于跨任务召回有帮助的偏好、习惯和历史背景。必须始终执行的团队规则应放在 `AGENTS.md`、Skill 或受版本控制的文档中。Memory 不得成为权限、审批或业务事实的唯一来源。

当前 RocketX 管家使用 Codex 原生本地 Memory；具体边界见 [Memory 规格](memory.md)。

## 6. 安全边界必须可见

- 读、写、网络和危险操作由明确权限档及运行时沙箱控制。
- 需要用户输入或批准时，问题回到发起它的任务，不串到其他会话。
- 结构化写入在确认前保持零副作用；结果未知时禁止自动重试写操作。
- 网页版、桌面端和无 Codex 状态必须真实呈现能力差异，不能保留必然失败的伪入口。

## 7. 完成定义

一项功能只有同时满足以下条件才算完成：

- 主流程真实可运行，不只是静态界面或 mock；
- 平台、依赖和权限边界明确；
- 加载、空、失败和恢复状态可理解；
- 数据落点和同步范围明确；
- 至少有一条自动化或真实运行证据；
- 能力矩阵、功能规格和测试追踪保持一致。
