# RocketX 功能规格

这里是 RocketX 功能行为的产品级事实来源。它回答五个问题：用户能做什么、从哪里进入、在哪个平台可用、失败时看到什么、用什么证据证明。

规格描述的是用户可感知的能力，不重复组件实现。实现方案可以变化，但对外行为、边界和验收标准变化时，必须同步修改对应规格。

## 阅读顺序

1. [产品原则](product-principles.md)：GTD、注意力与“确定性界面 + AI 执行”的共同约束。

3. 下方能力域规格：查看入口、流程、状态、数据、失败表现和验收证据。
4. [追踪索引](traceability.md)：从规格 ID 定位实现与自动化测试。

## 状态词

| 状态 | 含义 |
| --- | --- |
| `已实现` | 主流程已存在，并有自动化或真实运行证据 |
| `部分实现` | 主流程存在，但规格中的重要分支或平台尚未完成 |
| `受限可用` | 只有满足明确的平台、版本、登录或服务端条件时可用 |
| `未实现` | 当前没有可用主流程；可能只有入口、占位或计划 |
| `不适用` | 该平台或场景按产品定义不提供此能力 |

“上游支持”不等于“RocketX 已实现”。例如 OpenAI Docs 描述了网页版 Scheduled，并不能证明 RocketX 网页版已经接入该执行面。

## 平台词汇

- `桌面端`：Tauri 壳中的 RocketX；可调用本地文件、系统能力和 Codex 进程。
- `网页版`：浏览器中的 Vite Web 客户端；不能直接调用 Tauri 命令或访问任意本地目录。
- `兼容 Codex`：已登录、具有 `app-server`，且通过 RocketX 版本与握手门禁的 Codex 运行时。
- `可用 DSH`：桌面安装资源中存在固定 DSH 运行树，系统 Node.js 为 22.19+ 或 24+，需要执行时已配置 DeepSeek API Key。
- `无 Codex`：没有可解析的系统、标准安装或手动指定运行时。
- `性能模式`：保留常规 Rocket.Chat 功能并关闭 AI、管家、例行任务和本地 OCR 等高开销能力。

## 事实优先级

出现冲突时按以下顺序判断“当前状态”：

1. 当前工作树可执行行为和真实集成验证；
2. 当前自动化测试；
3. 当前生产代码；
4. 本目录规格；
5. 历史设计、实施记录、README 或 changelog；
6. 上游产品文档。

发现规格落后时，应先按代码和测试修正规格；如果代码违反已确认的产品契约，则另开实现变更，不能在规格中悄悄改写目标。

## 规格变更规则

- 新增用户可感知能力时，必须更新能力矩阵、对应能力域和追踪索引。
- 改变入口、权限、数据落点、平台支持或失败语义时，必须更新对应规格。
- 只重构内部实现且行为不变时，不需要改规格。
- `已实现` 必须给出证据；只有静态入口或 mock 截图不能标为 `已实现`。
- 计划能力写入“差距与目标”，不得混入当前流程。

新增能力域时使用 [规格模板](template.md)。
